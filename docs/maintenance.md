# Maintenance and next decisions

Triage by consequence: first privacy/unauthorized action or fabricated approval, then invented evidence/observations, then decision usefulness and installation friction. Record reproduction, affected version, repair and regression evidence. Keep a known-limits list instead of silently changing claims.

Review the public backlog when actual feedback is available. Do not add new domains or a web interface just because implementation is easy. Favor a change that resolves a recurring obstacle or makes one domain materially more useful. User outcomes to seek: voluntary repeat use, an observable decision improved, a recommendation rejected for an informative reason, and correction effort. Stars alone do not measure these.

Suggested next-stage choices:

- Continue alpha: real users can understand the card but evidence and usefulness remain preliminary.
- Focus a domain: repeated use indicates one medium has clearer needs and stronger feedback access.
- Run the formal comparison: a stable version, chosen model budget and independent reviewers are available.
- Pause expansion: core recommendations remain generic or creator access is insufficient to learn.

These are conditional options for the maintainer, not a decision already made. No automated outreach, telemetry, recurring job or subscription is configured. Breaking schema changes require explicit migration with retained originals. Update the ledger with actual evidence and limitations, not just generated files.
