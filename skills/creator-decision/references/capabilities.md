# Capability boundaries

Describe actual capability and actual use separately. Availability does not imply a tool was used.

| Material | Valid observation | Not established |
|---|---|---|
| Text, script, outline | Structure, task promise, narrative progression, contradictions | Finished audiovisual performance or market demand |
| Screenshots/frames | Visible composition, hierarchy, local continuity | Working controls, continuous pacing, full-work quality |
| Transcript | Words and information | Vocal delivery, timing, mix |
| Audio | Only inspected segment when audio processing exists | Unheard segments or all viewers' responses |
| Video | Actual inspected times/modalities | Hands-on game feel; entire work from a brief sample |
| Interactive prototype | Recorded tasks actually performed | Untested devices, users, integrations or long-term value |

If access fails, identify the failed material, continue on available evidence, and request only the missing portion that affects the recommendation. Never bypass access restrictions to create an impression of completeness.

With no network, use supplied materials and mark external facts unverified. With no execution/write access, return the card in conversation and explicitly say no saved/programmatic checks occurred. The optional Python helper runs locally but the host model/tools may process input remotely: no claim of wholly local inference or zero data transmission.
